# 대표 실패 사례 (OpenCV Grid + Spanning Reconstruction)

- 이미지: sample.jpg / 평가: evaluate.py, sample.jpg_gt.json (GT 95셀), 예측 = cells_original.json
- IoU 0.5 기준 놓친 GT 17개(FN), 잘못 잡은 예측 8개(FP)의 원인을 분류함

## F1. 한 행짜리 짧은 세로 경계 누락 → 과다 병합 (유형: line detection failure)
- 상황: 하단 표의 "대리인" 행과 공인중개사 영역(대표 / 등록번호 / 소속공인중개사 행)은
  "주소 | 값", "서명및날인 | 값", "등록번호 값 | 전화 | 번호"처럼 한 행 안에서만 짧은 세로선으로 나뉨
- 결과: 짧은 세로선을 놓쳐 라벨 칸과 값 칸이 하나의 merged 셀로 합쳐짐
  - 놓친 GT 11개: 38, 39 (대리인 "주소"), 72, 73, 76, 85 (서명및날인), 74, 75, 86, 89, 94 (등록번호·전화)
  - 합쳐진 예측 셀: id 43, 59, 74, 76, 78, 80, 85
- 원인: 세로선 길이(한 행 높이 약 60~68px) < 선 추출 open 커널(30 x 스케일 2.54 = 약 76px)
  → 선 추출 단계에서 선이 지워져 grid에 들어가지 못함 (피드백 3.1의 "짧은 내부 경계 누락")
- 검증: line_open_base를 24(약 61px)로 줄이면 셀 95개, TP 78 → 89, Precision/Recall 93.7%
- 조치: 2차 GT 이미지에서도 개선되는지 확인한 뒤 값 고정 예정 (한 장에만 맞춘 튜닝 방지)
- 그림: ![F1](img/F1_short_line.png)

## F2. 예측과 GT의 좌표 기준 불일치 (유형: 평가 연동 오류)
- 상황: GT는 원본 sample.jpg 위에, 예측(cells.json)은 기울기 보정본(sample_aligned.png, 1.06° 회전 + 캔버스 확장) 위의 좌표
- 결과: 같은 칸인데 약 50px 어긋남 (예: 소재지 라벨 칸 GT [270,718,503,777] vs 예측 [320,719,560,778])
- 영향 (IoU 0.5):
  | 예측 파일 | TP | Precision | Recall |
  |---|---|---|---|
  | cells.json (보정본 좌표) | 32 | 37.2% | 33.7% |
  | cells_original.json (원본 좌표) | 78 | 90.7% | 82.1% |
- 조치: 원본 좌표로 되돌린 cells_original.json / cells_primitive_original.json 출력 추가 (해결)

## F3. 촬영 원근 때문에 bbox 정밀도 저하 (유형: 기울기 보정 한계)
- 상황: 휴대폰 촬영으로 표가 사다리꼴로 찍힘. 회전 보정만으로는 모든 선을 똑바로 펼 수 없음
- 결과: 칸은 맞게 찾았지만 경계가 조금씩 어긋남. 맨 왼쪽 열은 첫 글자가 잘리기도 함 (예: "보증금"의 "보")
  - 소재지 값 칸 id 2: IoU 0.54 / 잔금 금액 칸 id 29: IoU 0.58 / 공인중개사 영역 id 45: IoU 0.52
  - IoU 기준을 0.5 → 0.7로 올리면 TP 78 → 68
- 조치: 원근 보정(호모그래피)은 후속 과제. ROI OCR 담당에게 "가장자리 글자 잘림 가능" 전달
- 그림: ![F3](img/F3_perspective.png)

## F4. (개선 전) 이전 코드의 표선 전체 소실 (유형: line detection failure)
- 상황: 이전 코드(TestReult.py)는 선 추출 커널이 이미지 높이의 40%
- 결과: sample.jpg에서 표선이 전부 지워져 "표선 검출 실패 (행 0개, 열 0개)", cells.json 생성 불가
- 조치: 커널을 해상도 비례 고정 길이로 바꾸고 표별로 분리 처리 → 현재 코드는 셀 86개 검출

# 공통 10장 대표 실패 사례

- 입력: tail 공통 10장 (`data/common10/`), 실행: `python Task_10_Renewal.py` (Task_0930.py 그대로, 파라미터 변경 없음)
- 근거: 각 `report.json` 의 `failures`, `output/common10/failure_cases.csv`, 선 추출 그림 `vis/0_lines.png` (재실행 시 생성)
- 10장 중 성공 2 / 부분 3 / 실패 5 (`docs/07_common10_results.md`)
- 공통 원인: 휴대폰 촬영의 **원근(사다리꼴)·종이 휨**. 회전 보정은 페이지 전체를 한 각도로만 돌리므로,
  보정 후에도 가로선들이 서로 평행하지 않고 위치마다 기울기가 다르다.

## F5. 하단 표 통째로 누락 — status 는 grid_fail 이 아니라 check (sample_5, sample_7, sample_10)
- 결과: 하단 표(임대인·임차인·공인중개사)가 결과에 없음. 표 수 1개
- 원인: 하단 표의 선은 추출됐지만(0_lines 에서 주황 = grid 에서 빠진 선), 기울어진 가로선들의 투영 범위가 서로 이어져
  `cluster_positions()` 에서 **행이 1개로 합쳐짐** → `rows < 2` 라 표가 아니라고 보고 건너뜀
  - sample_5 하단 표: 가로선 투영 band 폭 850px (행 높이 약 60px, 묶음 간격 기준 25px) → 행 1개
  - sample_7 하단 표: band 폭 889px → 행 1개
- 기록 문제: 표 하나라도 남으면 status 가 `check` 이고, 빠진 표는 `failures` 에 따로 남지 않음
  → 받는 쪽은 `manifest.json` 의 `tables` 가 2 미만이면 표 누락으로 처리 (07 문서 2절)
- 영향: tail 필드 중 임대인·임차인 성명 6개 (3장 x 2) 매칭 불가

## F6. 여러 행이 큰 셀 하나로 합쳐짐 (sample_3, sample_9, sample_5 상단)
- 결과: 상단 표 실제 11행 → sample_3 4행, sample_9 2행, sample_5 1행으로 복원. 계약내용 5행(보증금~차임)이 셀 1개로 합쳐짐
- 원인: F5 와 같은 행 투영 병합이 표 일부 구간에서만 일어남
  - sample_3 상단 표 행 band 폭 `[112, 403, 9, 4, 116]` px — 403px band 안에 실제 행 6~7개
- 자동 기록: sample_3 `over_merge` 4, `missing_boundary_misjudge` 10, `irregular_component` 1, `deskew_failure` 1 (보정 후 잔여 기울기 > 0.3°)
- 영향: 보증금·계약금 칸을 덮는 셀 높이가 GT 칸의 5.5~7.1배 → OCR 입력으로 쓸 수 없어 tail 전달에서 제외 (`reason: over_merged_cell`)

## F7. 한 장 안에서 표마다 결과가 갈림 (sample_8 상단, sample_6 상단)
- 결과: sample_8 상단 표 1x11 (1행으로 붕괴), 하단 표 11x14 정상 / sample_6 상단 표 3x11 (계약내용 행 누락), 하단 표 10x14 대부분 정상
- 원인: 종이가 위아래로 다르게 휘어, 같은 회전 보정이 하단 표에는 맞고 상단 표에는 맞지 않음
  - sample_8 `deskew_failure`: 1.07° 보정 후에도 잔여 기울기 기준(0.3°) 초과
- 의미: 이미지 단위 status 만으로는 부분 성공을 구분할 수 없음 → 필드 단위 매칭표 `field_cell_match.csv` 를 같이 전달

## F8. 원거리 촬영 + 배경 (sample_10)
- 결과: 문서가 화면 가로의 약 60% 크기로 작게 찍히고 책상·케이블이 함께 찍힘. 셀 3개, 하단 표 누락
- 원인: 2.32° 회전 + 원근으로 F5·F6 과 같은 행 병합 발생. 배경 모서리(책상 경계)도 긴 선으로 추출됨 (0_lines 주황 선)
  - 추정: 해상도 스케일을 이미지 전체 대각선 기준으로 잡으므로, 문서가 작게 찍히면 문서 크기 대비 선 추출·묶음 기준이 상대적으로 커짐 (미검증)
- 영향: tail 6개 필드 모두 사용 불가

## 정리 — 이번 작업에서 하지 않은 것
- 위 실패는 모두 원근·휨 보정(문서 4점 검출 → 호모그래피)이 없어서 생기는 한계로, F3(원근 정밀도 저하)의 심한 경우다.
- 작업 범위(새 검출기·병합 알고리즘 수정 금지)에 따라 파라미터와 알고리즘은 바꾸지 않고 결과를 그대로 기록했다.
